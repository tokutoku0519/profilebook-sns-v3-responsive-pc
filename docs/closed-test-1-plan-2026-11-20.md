## 2. 確定した仕様による、既存コードへの影響

### ① プロフ交換 ＝ 相互フォロー

**いまの状態（3 つが別々）**

| 状態 | 置き場所 | 使われ方 |
|---|---|---|
| フォロー | DB `follows`（だれでも読める） | フォローボタン・相互フォローの判定・なかよし度 |
| 「なかよし」（承認制のプロフ帳交換） | DB `friendships`（申請 → 承認） | 他人のプロフィールの 📖 ボタン・なかよし度・マイページの一覧・通知（申請・承認） |
| 交換済みの一覧（古い仕組み） | 端末だけ（localStorage `miri_exchanged_profiles`） | 画面には使われていない（残骸） |

**新しい設計**

- プロフ交換は、**`follows` から計算するだけ**にする（A→B と B→A の両方があれば交換中）。別の状態を持たないので、フォローと交換が食いちがうことが原理的に起きない。Web・iOS・Android で同じ表示になる。
- 成立・解除の通知：`follows` に追加されたとき、逆向きもあれば「プロフ交換が成立」の通知を両者に出す（DB のトリガー）。フォローを外すと、交換も自動で終わる。
- 公開範囲：**変えない**。交換の成立を理由に公開しない。フォロワー限定は、今までどおり「フォローしているか」で決まる（相互フォローなら当然フォロワーなので見える）。
- `friendships` テーブル：アプリから使わなくなる。データは消さない（互換のため残す）。本番は自分の 2 アカウントだけなので、移行は不要の見込み。
- localStorage の `miri_exchanged_profiles`：読み書きをやめる。

**画面への影響（ご判断が必要な点）**

- 他人のプロフィール：📖「交換を申請」ボタン → フォローボタンと一体化（相手がフォロー済みなら「フォローし返してプロフ交換」）。
- **なかよし度（0〜5）**：今は「相互フォロー」と「プロフ交換」が別々に 1 点ずつ。同じものになるので、**① 4 点満点にする ② 別の行動（例：コメントしあった）を 1 つ足して 5 点を保つ**、のどちらかを決めていただきたい。
- マイページの「なかよし」一覧 → 相互フォローの一覧。「申請が届いています」→「フォローされています（まだ返していない人）」。
- 注意：いまの `follows` はだれでも読める（ログインしていない人も）ので、**だれとだれがプロフ交換しているかも公開になる**。フォロー一覧を非公開にするかは、別に決める必要があります。

見積もり：1〜1.5 日（DB のトリガー・画面・通知・翻訳の文言）

### ② プロフィール写真（Supabase Storage）

**いまの状態**

| 写真 | 保存先 | 問題 |
|---|---|---|
| プロフィールアイコン | 端末で縮小した画像を文字（data URL）にして、DB の `profiles.avatar_url` に直接入れている | 一覧を読むたびに大きな文字列を運ぶ（重い）。形式の確認がない |
| お気に入り写真 | **端末だけ**（localStorage `favoritePhotos`） | 別の端末・ほかの人には見えない。端末を変えると消える |
| 日記・ブログの写真 | `photo_url` の列（data URL の可能性） | アイコンと同じ |

**新しい設計（案）**

| 項目 | 内容 |
|---|---|
| バケット | `avatars`（公開読み取り。アイコンはプロフィールと同じく公開）／`profile-photos`（非公開。お気に入り写真など公開範囲があるもの） |
| 置き場所 | `<ユーザーID>/<ランダムな名前>.webp`。ファイル名は利用者に決めさせない |
| 書きこみの権限 | Storage の RLS で「自分のフォルダー（先頭が自分の ID）だけ」に追加・変更・削除できる |
| 読む権限 | 非公開バケットは、写真ごとの公開範囲（公開／フォロワー限定／自分だけ）を表に持ち、RLS で読める人だけに「期限つきの URL」を出す |
| 大きさ・形式 | 端末で長い辺 1280px・WebP（または JPEG）に作り直してから送る（**位置情報などの EXIF が消える**）。バケットの設定で 2MB まで・`image/jpeg, image/png, image/webp` だけを許可（SVG は不可：スクリプトを埋めこめるため） |
| 不正なファイル | 作り直せない（画像として読めない）ファイルは送らない＋バケット側で形式・大きさを拒否 |
| 枚数 | お気に入り写真は 1 人 6 枚まで（DB で制限） |
| 削除・変更 | 古いファイルを消してから新しい名前で保存（キャッシュに古い画像が残らない）。退会時は本人のフォルダーを消す（退会の処理に追加） |
| 今の data URL | 表示はそのまま使えるようにし、次にログインしたとき Storage へ移す（データは失わない） |

**Free プランでの注意（数値は公式の料金ページで要確認。この作業環境から supabase.com を読めなかったため）**

- Storage の合計容量と、月の転送量に上限がある（Free は 1GB・数 GB/月 程度の想定）。1 枚 200KB 前後にすれば、10〜50 人のテストでは十分に収まる見込み。
- 画像の自動変換（サイズ変更）は有料プランの機能のため、**端末で縮小してから送る**設計にする。
- しばらく使わないと、プロジェクトが一時停止されることがある。テスト期間中は毎日使われるので問題になりにくいが、正式リリース前に有料プランを検討。

見積もり：2〜3 日（バケット・RLS の SQL、アップロード・表示・削除、今の写真の移行、退会時の削除、テスト）
