## 8. Web・iOS・Android のデータ共通化・引き継ぎ設計

**方針**：Web とアプリは**同じ本番の Supabase（認証とデータ）**を使う。データのコピーはしない。

| 項目 | 設計 |
|---|---|
| アカウント | Supabase Auth のユーザー ID が、Web とアプリで同じ。テスト①で作ったアカウントをそのまま使い続ける |
| プロフィール・プロフ帳・回答・投稿・日記・フォロー・交換・投票 | すでにサーバー（本番 DB）にある。交換は T1-06 でサーバー側に統一 |
| 写真 | T1-04 で Supabase Storage。アプリも同じ URL を表示 |
| コイン・ガチャ・着せ替え・テーマ・フォント | 今は `book.__game`（サーバーにある）。R-04 で台帳に移す |
| ブックマーク・コインの履歴・通知の設定・言語 | R-03 でサーバーへ |
| 端末のデータの役割 | 「表示を速くするための写し」だけにする（消えても困らない） |
| テストのデータと残すデータの区別 | **テスト参加者のデータは、すべて残すデータとして扱う**（消さない）。あなた・私が作る試しのアカウントは、本番では作らないのが原則（試しは `miri-staging`）。本番で必要な場合は `@example.com` は使えないので、あなたのメールの別名（`+miri-test`）で作り、一覧に記録する。正式版の前に、その一覧のアカウントだけを、あなたの承認を得て 1 件ずつ削除する |
| DB の変更 | 番号つきの移行ファイル（`supabase/migrations/0001_…sql`）で、検証用 → 本番の順。適用の前にバックアップ。取り消し用の SQL も一緒に用意 |
| 禁止 | 本番 DB の初期化・既存データの一括削除はしない |

**テスト①を検証用（miri-staging）で行い、あとで本番に移す案は勧めない**：ログインの情報（パスワード）を含めてアカウントを別のプロジェクトへ移すのは手順が重く、失敗したときに取り返しがつかないため。

## 9. 本番 Supabase と miri-staging の役割

| | 本番 Supabase | miri-staging |
|---|---|---|
| 用途 | テスト①から正式版まで**実際の利用者のデータ**を保存（引き継ぐ） | 開発・翻訳・ダミーデータの検証 |

**本番を使うときのアクセス制限**：新規登録を止めて招待だけにする（T1-11）。アプリの画面はログインしないと見られない（公開ブログの記事だけは見えるので、テスト中は検索エンジンに出さない）。

## 11. 課金機能を後から付けるための設計上の注意点（実装はしない）

| 項目 | 考慮すること |
|---|---|
| 有償・無償コインの区別 | 残高を 2 つに分ける（有償・無償）。使う順番（無償から先など）を決めて記録する |
| 残高・取引履歴 | **台帳（取引 1 件ごとの行）**をサーバーに持ち、残高は台帳から計算できるようにする。書き換えはサーバーの関数だけ（R-04） |
| 不正付与の防止 | 本人が直接書けない。付与は決済の確認（署名・レシートの検証）のあとにサーバーだけが行う。同じ購入で 2 回付与しない（購入 ID で重複を防ぐ） |
| ストア内課金との連携 | iOS・Android でデジタルの品（コイン・テーマ・サブスク）を売るには、原則としてストアの課金が必要。Web で買ったコインをアプリで使えるかは各ストアの規則による（要確認） |
| 返金・購入の復元 | 返金の通知（Apple・Google・Stripe）を受けてコインを戻す処理。テーマなど「持ち続けるもの」は所有をサーバーに記録し、どの端末でも復元できる |
| 法務 | 有償コインは**資金決済法の前払式支払手段**に当たりうる（未使用残高の基準・届出・供託など。有効期間の設計で扱いが変わる）。ガチャは**景品表示法**（コンプガチャの禁止）と業界の指針（確率の表示）。**特定商取引法の表記**（`/tokushoho` は既にある）。未成年の購入の上限・保護者の同意。いずれも要法務確認 |
| 公認クリエイターのサブスク・限定の閲覧 | 閲覧の権限をサーバー側（RLS）で判定する。いまの「限定コンテンツ」は端末の印（`miri_premium_content`）なので、作り直しが必要 |
