## 1. 対象と原則

- 対象：**公開プロフィールの自由回答だけ**。
  - 例：`motto`、`dream`、`specialty`、`__questions.3.a`、`__best3.drink.0`、`__monthly.episode`
  - 名前・ニックネーム・ID・誕生日・血液型・出身地などは対象外。
  - 日記・ブログ・コメント・サークル・限定公開は Phase C 以降。
- 原文は変更しない。翻訳は `content_translations` に置き、表示を切り替えるだけ。
- **クライアントは文章を送らない**。送るのは「ユーザー名・項目の場所・翻訳先の言語」だけで、原文はサーバーが DB から取り出す。
- 翻訳するのは「翻訳を見る」が押されたときだけ。自動では訳さない。
- 失敗・予算切れ・停止中・権限なしのときは**原文を表示**する。翻訳済みのキャッシュは予算切れでも表示する。

## 2. 公開範囲の現状（調査結果）と翻訳の対象

### 今の仕様

| 項目 | 公開範囲の設定 | 未設定のときの扱い |
|---|---|---|
| 基本情報 19 項目（motto・dream・specialty など） | 編集画面のチップで `public` / `followers` / `private` を選べる（`book.__visibility[項目名]`） | 画面は「公開」と表示し、`get_visible_book` も全員に見せる |
| ひとこと質問（`__questions`）・BEST3（`__best3`）・今月の BEST3（`__monthly`） | 設定がない | 常に全員に見せる |
| コイン・購入履歴など（`__game` / `__purchases`） | ― | 本人以外には見せない |

- 公開範囲は項目（トップレベルのキー）単位で、値は `public` / `followers` / `private` の 3 種類だけ。
- コミュニティ限定やブロックはプロフ帳にはまだない。

### SQL 案での扱い

- 翻訳してよいのは、`get_visible_book`（画面の表示と同じ関数）が**ログインしていない人に返す内容**の中だけ。表示の規則が変われば翻訳も自動でそれに従う。
- さらに次の条件を重ねる。
  - 公開範囲が `public` 以外の項目は翻訳しない。`followers`・`private`・今後増える値（コミュニティ限定など）はすべて対象外。
  - 翻訳してよい項目の一覧（`profile_fields`）に入っているものだけ。名前・誕生日などは入れない。
  - 400 文字以下の文字列だけ。入れ子の場所を指定できるのは `__questions` などの組み立て項目だけ。
- **未設定の扱い**は `require_explicit_public` で切り替える。初期値は「明示的に公開を選んだ項目だけ」。
  - この設定のままだと、ひとこと質問・BEST3 には公開範囲の設定がないので翻訳されない。
  - 基本情報の 19 項目も、本人がチップを触っていなければ未設定なので翻訳されない。

### 判断が必要なこと（下の 3 案から選ぶ）

1. **本人の「翻訳を許可する」設定を新しく作る（おすすめ）**
   - 本人が許可した人の、公開の項目だけを翻訳する。
   - 外部の翻訳サービスへ文章を送ることへの本人の同意にもなる。
   - プロフ帳の編集画面に切り替えを 1 つ追加し、SQL の判定に 1 行足す。
2. **ひとこと質問・BEST3 にも公開範囲のチップを付ける**
   - 明示的に「公開」を選んだ項目だけを翻訳する。
   - 今のチップは最初から「公開」と表示されているので、明示的に選んだかどうかを画面で区別する工夫がいる。
3. **未設定も公開とみなす**（`require_explicit_public = false`）
   - 表示の規則とそろうが、本人が知らないうちに外部へ送られる。

## 3. 処理の流れ（`POST /api/translate`）

```
リクエスト  { kind: "profile_field", owner: "<username>", path: "__questions.3.a", target: "en" }
ヘッダー    Authorization: Bearer <Supabase のアクセストークン>（ログイン必須）

 1. 停止スイッチ：環境変数 TRANSLATION_ENABLED が "true" でなければ { status: "original" }
 2. 入力の検査：kind は許可リスト、path は形式チェック、target は 20 言語のどれか
 3. ログイン確認：supabaseAdmin.auth.getUser(token) → 依頼者の user_id（回数制限に使う）
 4. 翻訳済みを返す：rpc('get_profile_translation')
      → 関数の中で、公開範囲と原文の一致を毎回確かめてから返す
 5. 翻訳中の目印：rpc('claim_profile_translation')
      → 取れなければ（ほかで翻訳中・権限なし）原文を返す。翻訳中なら数秒後に 4 からやり直す
 6. API を呼ばない判定：空白・記号・絵文字・数字だけ／翻訳先と同じ言語／用語集の「訳さない語」と完全一致
      → store(kept) して原文を返す
 7. 予算の確保：rpc('reserve_translation', 依頼者, 原文の持ち主, 見込み額)
      → disabled / budget / user_limit / owner_limit なら原文を返す
 8. Claude Haiku 5.5 で翻訳（4 章）。タイムアウト 15 秒
 9. 検証：JSON として読める／改行の数が同じ／絵文字とデコ記号が残る／
      訳さない語がそのまま含まれる／ローマ字化していない → だめなら failed
10. 精算：rpc('settle_translation', 確保の ID, 応答の usage にある 4 種類のトークン数)
      → 実額は DB の料金表で計算する
11. 保存：rpc('store_profile_translation')
      → 保存する瞬間にも、原文と公開範囲が変わっていないか確かめる
12. 返す：もう一度 4 を通してから返す（翻訳中に非公開へ変わった場合に返さない）
```

**返り値**：`{ status: "done" | "kept" | "original", text?: string }`

- 原文はブラウザがすでに持っているので、返さない。
- 失敗の理由（予算切れ・回数制限など）は画面に細かく出さず、「いまは翻訳できません」とだけ表示する。

**見込み額**：`(1,300 + 原文の文字数 × 3) × $0.10/M + 400（max_tokens）× $0.50/M`

- 400 文字なら約 $0.00045。上限 `max_estimate_usd = $0.002` を超える見込みは DB が受け付けない。
- 実額は必ず見込み額以下になる。入力は system と文字数で上限が決まり、出力は max_tokens で頭打ちになるため。

## 4. Claude Haiku 5.5 の呼び出し

- モデル：`claude-haiku-5-5`（環境変数 `TRANSLATION_MODEL`）。
- 思考：`thinking: { type: "disabled" }`、`effort: "low"`。
  - Haiku 5.5 は思考が既定でオンで、その分も出力料金になる。止められるのは effort が high 以下のとき。
- 出力：`max_tokens: 400`、構造化出力（JSON スキーマ）で次の形に固定する。
  `{ "decision": "translated" | "kept_original", "translation": "…", "kept_terms": ["…"] }`
- system（固定。プロンプトキャッシュの最小 512 トークン以上にする）：
  - プロフィール帳の回答を {原文の言語} から {翻訳先} へ訳す。訳文だけを返し、説明や注釈を足さない。
  - 人名・@ID・アーティスト名・グループ名・曲名・作品名・商品名・ブランド名・地名・コミュニティ名は原文のまま。
    - 正式な海外名称が広く使われている作品・商品だけは置きかえてよい（例：鬼滅の刃 → Demon Slayer）。
    - 推測で別の作品名・人名にしない。
  - 若者言葉・略語・造語は、意味がはっきりしていれば自然に訳す。迷ったら `kept_original`。
  - ローマ字にしない。改行・絵文字・デコ記号（`[♥]` など）はそのまま残す。
- user：`<question>{質問文}</question><answer>{回答}</answer>`
  - 質問があると「嵐」がアーティストか天気かを判断できる。
  - 公式の質問は ID から日本語を取る。
- 用語集：まず JSON ファイル（運営が管理）で始め、一致した語だけを system の末尾に追記する。
- 使わない機能：Batch API（29 日保存）、Files API。

## 5. 費用と予算の守り方

### 料金と 1 回の費用
公式料金（2026-10 時点）：入力 $0.10、出力 $0.50、キャッシュ読み取り $0.01、キャッシュ書き込み（5 分）$0.125（いずれも 100 万トークンあたり）。

| ケース | 入力 | 出力 | 1 回の費用 |
|---|---|---|---|
| プロンプトキャッシュなし | 800 | 50 | $0.000105 |
| プロンプトキャッシュあり（700 を読み取り） | 100＋キャッシュ 700 | 50 | $0.000042 |

※ トークン数は推定。比較テストで実測して更新する。

### 月の試算（試験運用中はプロンプトキャッシュが切れやすいので「なし」で見積もる）

| 想定 | 「翻訳を見る」の回数 | 翻訳済みを返す割合 | API 呼び出し | 月額 |
|---|---|---|---|---|
| 小 | 6,000 | 30% | 4,200 | 約 $0.44 |
| 中 | 30,000 | 40% | 18,000 | 約 $1.89 |
| 目標 $5 | ― | ― | 約 47,000 | $5 |
| 上限 $10 | ― | ― | 約 95,000 | $10 |

### 同時アクセスでも上限を超えない仕組み（SQL の `reserve_translation`）

1. 呼び出す前に見込み額を確保する。月の行を `FOR UPDATE` でロックするので、何件同時に来ても 1 件ずつ判定される。
2. 「確定額＋呼び出し中の見込み額＋今回の見込み額」が上限を超えるなら呼ばない。
3. 呼び出し後に、API の応答にある実際のトークン数から実額を計算して精算する（`settle_translation`）。
4. 精算されないまま 15 分たった確保（サーバーが途中で落ちたなど）は、見込み額を全額使ったとみなして確定する。実額より少なく数えることはない。
5. 確保した月で精算するので、月をまたいでもずれない。

**確認結果**：上限ちょうど 10 件分の予算に 40 件を同時に送ると、通ったのは 10 件だけで、確保額は上限ちょうどだった。

### 上限に達したとき
- 新しい翻訳だけを止める。翻訳済みは引き続き返し、それ以外は原文を表示する。
- 目安の $5 を超えたら運営に知らせる。止めはしない。

### Anthropic 側の上限（予備）
- 翻訳専用のワークスペースを作り、月 $10 の上限を設定する（既定のワークスペースには設定できない）。上限に達すると API はエラーを返し、Miri は原文を表示する。
- Anthropic 側の集計の反映時刻は公式に明記がないため、厳密な上限は Miri 側で守る。

### 利用状況の見方
- SQL Editor で `translation_budget` を見る：月ごとの確定額・呼び出し中の額・回数・翻訳済みを返した回数・トークン数。確認用のクエリは SQL ファイルの末尾にある。

## 6. 権限の設計（service_role を使う前提）

| 確認したいこと | 設計 |
|---|---|
| service_role は RLS を通らない | 翻訳表に直接触るのはサーバーだけで、判定はすべて SECURITY DEFINER の関数の中で行う。原文の取り出し・翻訳済みの返却・保存のどれも、関数が公開範囲を確かめる |
| ユーザーの権限を持ち込まない | 原文の取り出し関数は、ユーザーのトークン付き（`auth.uid()` あり）で呼ばれると何も返さない。フォロワーの権限で限定公開の項目が取り出されることはない |
| 関数の実行権限 | 6 つの関数とトリガー関数は、PUBLIC・anon・authenticated から実行権限を外し、service_role だけに付ける。Supabase は新しい関数に既定で実行権限を付けるので、明示的に外す。どの関数も `search_path = public` を固定する |
| テーブル | RLS 有効・ポリシーなし。anon・authenticated の権限も外す（Supabase の既定の付与を外す） |
| 翻訳キャッシュが別ユーザーに渡らないか | 対象は「誰でも見られる公開項目」の訳だけなので、ほかの人に返してよい内容。返すたびに公開範囲と原文の一致を確かめるので、非公開にした後や編集した後の訳は返らない |
| 退会・原文の編集・公開範囲の変更 | 退会は外部キーで削除。原文の編集はトリガーでその項目の訳を削除。公開範囲の変更はトリガーでその人の訳をすべて削除。保存の瞬間に変わっていた場合は保存しない |
| 大量リクエスト・悪用 | 下の 7 点で防ぐ |

**大量リクエスト・悪用への対策**
1. ログイン必須。
2. 1 人 1 日 30 回まで（`daily_user_limit`）。
3. 同じ人の原文が 1 日に新しく訳されるのは 60 回まで（`daily_owner_limit`）。編集を繰り返して費用を増やすのを防ぐ。
4. 月の上限。
5. 翻訳済みは API を呼ばない。
6. 対象は 400 文字以下の決まった項目だけ。
7. 必要なら Vercel Firewall の回数制限を `/api/translate` にかける。

**今後の拡張（限定質問・限定ブログ・サブスク限定など）**

- `source_type` と、それぞれの「原文を取り出す関数（閲覧者を受け取って判定する）」をセットで追加する。
- 翻訳の行には、訳したときの公開範囲（`audience`）を持たせる。
- 限定公開の訳は、閲覧者ごとに毎回権限を確かめる関数を通さないと返せない形にする。今の check 制約は `public` しか許していない。

## 7. SQL の確認結果（ローカルの PostgreSQL 16・Supabase 相当の環境）

実際の Supabase では未確認。環境はロール・`auth.uid()`・既定の権限付与・`get_visible_book` を本番と同じ定義で再現した。

**anon・ログイン中のユーザーから**
- 5 つのテーブルを読めない。
- 6 つの関数を実行できない。
- 設定を書き換えられない。
- 翻訳表に書き込めない。

**原文の取り出し**
- 明示的に公開した項目だけ取り出せる。

**目印・保存・返却**
- 二重の翻訳を防ぐ。
- 翻訳済みには API を呼ばない。
- 原文と一致しない保存は拒否する。
- 翻訳中に原文が編集されたら保存しない。
- 公開範囲の変更で訳を削除する。行が残っていても返さない。
- 関係ない項目の編集では訳を残す。
- 退会で訳を削除する。

**予算**
- 停止中は呼ばない。
- 上限で止める。
- 使用量から実額を計算する（800＋50 トークン → $0.000105）。
- 二重の精算をしない。
- 放置された確保は見込み額で確定する。
- 1 人・1 原文あたりの回数で止める。
- 月をまたいだ精算は確保した月に入る。
- 40 件を同時に送っても上限を超えない。

**取り消し**
- 実行するとテーブルと関数がすべて消え、原文は変わらない。
- 取り消し後も編集でき、再適用もできる。

## 8. データの扱い（Anthropic）

- **保存期間（標準）**：API の入力・出力は受信または生成から 30 日以内にサーバー側で自動削除される。
  - 例外：Files API を使う場合、ゼロデータ保持（ZDR）の契約がある場合、利用規約違反の調査や法令対応で長く保存する場合。
  - 安全性の判定で違反とされた内容は、最長 2 年保存される。
  - 出典：[How long do you store my organization's data?](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)。このページはこの作業環境からは開けず、検索結果の要約で確認した。正式には契約前にご自身で確認が必要。
- **学習への利用**：API の入力・出力は、明示的な許可なしにモデルの学習に使われない。
- **使う機能の条件**：Messages API（通常の呼び出し）とプロンプトキャッシュだけを使う。Batch API（29 日保存）と Files API は使わない。
- **Haiku 5.5**：30 日保存が必須の「Covered Models」ではない。
- **送る内容**：公開項目の文字列と質問文だけ。ユーザー名・ID・メール・アクセストークンは送らない。
- **プライバシーポリシー**：翻訳サービス（外国の事業者）への提供の記載を、導入前に追記する。

`npm run check:i18n` で両方を別々に表示する。

### ko・zh・zh-tw・th の統合（既存の回答との互換を優先）

- いまは言語ごとに別のお題（各 20 問。ID は `kq1`・`zhq1`・`twq1`・`thq1` など）を出題している。回答は `question_key` にその ID で保存されている。
- 共通 ID（`d1`〜`d366`）の訳が全問そろい、品質が `reviewed` 以上になった言語から、新しい出題だけを共通 ID に切り替える（`sharedPoolReady`。実装済み）。
- 既存の回答の ID は変えない。旧 ID のお題の文は残し、過去の回答の表示が壊れないようにする。
- 旧 ID と共通 ID が同じ意味のときは対応表（例：`kq3 → d12`）を持ち、検索・集計だけをつなぐ。
- 翻訳は「よく出るお題 → 季節のお題 → 残り」の順に少しずつ進める。各言語の話者が自然さと文化的な違和感を確認してから `reviewed` / `native` にする。

## 11. 段階

- **Phase A（今回）**
  - 外部の翻訳サービスへの送信を廃止（画面の自動翻訳を削除）。
  - 固定文言の翻訳キー化を順次進める。
  - 公式のお題の共通 ID と品質管理。
- **Phase B（承認後）**
  - 公開範囲の扱いを決める（2 章）→ SQL 適用 → API とボタン → 試験運用（月 $5 目標・$10 上限）。
- **Phase C**
  - 日記・ブログ・コメント・サークル（公開のもの）。
  - 限定公開は、閲覧者ごとの権限確認の関数ができてから。
- **そのほか**
  - 言語別の表示名（本人だけが設定）。
  - 趣味別プロフィール帳・公認ユーザーの独自質問・サブスク限定なども、同じ仕組みに `source_type` と権限の関数を足して広げる。
